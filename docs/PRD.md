## 1. Summary
We build a **2-player, Monopoly-rules property-trading game** on a 40-space board of Indian cities and railway stations. We train **reinforcement learning agents** (DQN, PPO and MaskablePPO) to play it against rule-based bots. Everything is shown in a **web game UI** with a real square board, animated dice and tokens, a "Human vs AI" mode, and an **"AI Brain X-Ray"** panel that shows *why* the agent made each decision. The academic core is a set of controlled experiments based on three published papers.

## 2. Problem & motivation
- Monopoly mixes chance (dice) with strategy (what to buy, when to build, how much cash to hold). Its huge action space has made it a common RL testbed.
- Published work goes from heavily simplified versions (Bailis et al. 2014; Arun et al. 2019) to the full 4-player game with trading (Bonjour, Haliem et al. 2022).
- Our question: **"In a simplified 2-player game, can an RL agent learn to beat a tuned rule-based player? Do action masking and reward design matter?"**
- We also want the result to be easy to see in a live demo, not just a number in a table.

## 3. Goals
| ID | Goal | Measured by |
|---|---|---|
| G1 | Faithful, tested game engine with Medium-depth rules | ≥ 90% unit-test coverage of rule functions; 10,000 random games with no crash or invariant violation |
| G2 | Trained agents that beat the baselines | Win rate vs Fixed-Policy bot, mean ± 95% CI over 1,000 games × ≥3 seeds (**no target number is promised in advance**) |
| G3 | Controlled experiments (design + reward ablations) | Results tables and plots generated by script from saved logs |
| G4 | Game-like, explainable UI | Board, tokens, dice, cards animate; X-Ray shows action probabilities/Q-values for every AI decision |
| G5 | Strong academic presentation | Web slide deck + README + verified literature review |

## 4. Non-goals (explicitly out of scope)
- Trading between players, auctions, 3+ players, the speed die
- Voluntary mortgaging/unmortgaging and the even-building rule (Medium rule depth, D-003)
- Online multiplayer, user accounts, persistence beyond a session
- Reproducing Hasbro/Funskool branding, artwork or card text (D-001)
- Self-play / league training, imitation learning (possible stretch only)

## 5. Users & personas
| Persona | Needs |
|---|---|
| **Professor / evaluator** | Understand the method in 5 minutes, play against the AI, see evidence the AI learned something, check the results are honest. |
| **Team members** | Clear ownership, a shared interface between engine/RL/API/UI, docs that let anyone (or an AI assistant) pick up work. |
| **Classmates at the demo** | A fun, good-looking game they can watch or play. |

## 6. User stories
1. *As an evaluator,* I open the app and press **"Watch AI vs Bot"**. I see the tokens move around a real board, and I can step turn-by-turn or auto-play at different speeds.
2. *As an evaluator,* at each AI decision I see the **X-Ray panel** with the probability (PPO) or Q-value (DQN) of each action, which actions were masked, and the reward it just received.
3. *As an evaluator,* I choose **"Play vs AI"**, roll the dice, decide to buy or build, and lose (or win) against the trained agent.
4. *As an evaluator,* I open the **Results** page and see win-rate learning curves, PPO vs DQN vs MaskablePPO vs bots, and the ablations, all with error bars.
5. *As a team member,* I run `pytest` and the training/eval scripts with one command each, and the results regenerate the plots used in the slides.
6. *As a presenter,* I open a web slide deck that tells the full story and links to the live demo.

## 7. Functional requirements

### 7.1 Game engine (`src/engine`)
| ID | Requirement | Priority |
|---|---|---|
| FR-E1 | 40-space board with verified Indian names, 8 colour groups, 4 stations, 2 utilities, 2 taxes, 3 Chance, 3 Community Chest, 4 corners | Must |
| FR-E2 | 2 players, ₹1,500 starting cash, ₹200 for passing/landing on GO | Must |
| FR-E3 | 2d6 movement; doubles grant another roll; 3 doubles in a row → jail | Must |
| FR-E4 | Rent: base; ×2 for an unimproved monopoly; 1–4 houses; hotel; stations 25/50/100/200; utilities 4×/10× dice | Must |
| FR-E5 | Building: only on full colour groups; a build adds 1 house to the least-developed property of the chosen group (keeps building even without a separate rule); max hotel | Must |
| FR-E6 | Jail: pay ₹50 or try for doubles; forced to pay and move on the 3rd failed attempt; Get-Out-of-Jail card | Must |
| FR-E7 | Chance & Community Chest: two fixed 16-card decks with **original** text, shuffled per game | Must |
| FR-E8 | Forced liquidation when cash < 0: sell houses at half cost, then mortgage at half price; bankrupt if still negative | Must |
| FR-E9 | Game ends at bankruptcy or after **200 rounds**; then the higher raw net worth wins | Must |
| FR-E10 | Deterministic given a seed; emits a structured **event log** (rolled, moved, passed GO, bought, paid rent, drew card, built, mortgaged, jailed, bankrupt) | Must |
| FR-E11 | Engine has no dependency on RL libraries or the web layer (pure Python) | Must |

### 7.2 Opponents (`src/bots`)
| ID | Requirement | Priority |
|---|---|---|
| FR-B1 | **Random bot:** buys with p = 0.5; builds with p = 0.5 when possible | Must |
| FR-B2 | **Fixed-Policy bot** (Bailis et al. 2014): buys/builds only when cash > ₹350, liquidates when cash < ₹150 | Must |
| FR-B3 | **Greedy bot:** always buys and builds when it can afford to | Should |
| FR-B4 | Rule-based jail policy shared by all bots and the RL agent (hybrid idea from Bonjour/Haliem et al.) | Must |

### 7.3 RL environments (`src/envs`)
| ID | Requirement | Priority |
|---|---|---|
| FR-R1 | **Env A "Blueprint":** Gymnasium env, Box(32), Discrete(3) asked every turn, invalid → Pass | Must |
| FR-R2 | **Env B "Masked":** queried only at decision points, Box(~123), Discrete(10), `action_masks()` for MaskablePPO | Must |
| FR-R3 | Reward modes: `delta_share` (default), `absolute_share` (blueprint), `sparse` (terminal only); terminal ±c configurable; bonus `b` configurable | Must |
| FR-R4 | Opponent selectable per env instance; starting player randomised | Must |
| FR-R5 | Both envs pass `gymnasium.utils.env_checker` and SB3 `check_env` | Must |

### 7.4 Training & evaluation (`src/rl`)
| ID | Requirement | Priority |
|---|---|---|
| FR-T1 | `train.py --algo {dqn,ppo,maskppo} --env {A,B} --opponent {...} --reward {...} --seed N --steps N` | Must |
| FR-T2 | Periodic evaluation callback: every 10k steps, 200 games vs each bot; logs to CSV/TensorBoard | Must |
| FR-T3 | `evaluate.py`: 1,000 games per (model, opponent); win rate, 95% CI (Wilson), mean game length, mean final net worth | Must |
| FR-T4 | `make_plots.py` creates every figure used in the slides/UI from logs and exports `results/*.json` for the frontend | Must |
| FR-T5 | Experiment configs live in `experiments/*.yaml` so results can be reproduced | Should |

### 7.5 Backend API (`src/api`, FastAPI)
| ID | Requirement | Priority |
|---|---|---|
| FR-A1 | `POST /api/games` creates a game `{mode: ai_vs_bot \| human_vs_ai \| bot_vs_bot, agent_id, opponent, seed}` | Must |
| FR-A2 | `GET /api/games/{id}` returns the full public game state | Must |
| FR-A3 | `POST /api/games/{id}/advance` runs until the next decision or end of turn; returns new events + state | Must |
| FR-A4 | `POST /api/games/{id}/action` sends a human decision (`roll`, `buy`, `pass`, `build:<group>`, `pay_jail`) | Must |
| FR-A5 | Every AI decision event includes an **X-Ray** payload: legal mask, action probs or Q-values, state-value estimate, reward components | Must |
| FR-A6 | `GET /api/agents` lists loaded models with metadata; `GET /api/results` serves experiment JSON | Must |
| FR-A7 | In-memory session store with TTL; CORS for the dev frontend | Must |

## 9. Success metrics (what goes on the "Results" slide)
- Win rate of the best agent vs the Fixed-Policy bot and vs the Random bot (mean ± 95% CI, ≥3 seeds × 1,000 games)
- Env A vs Env B: the effect of masking + decision points on final win rate and sample efficiency (steps to reach 60% of the final win rate)
- Reward ablation: delta_share vs absolute_share vs sparse
- Behaviour analysis: which colour groups the agent prioritises, average cash buffer kept, build timing
- Human-vs-AI: informal tally from team/classmate games during the demo (reported as anecdotal)

## 10. Risks & mitigations
| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| Agent fails to beat Fixed-Policy bot | Med | High | Masked env, reward ablations, longer training; an honest negative result with analysis is still a valid result |
| Engine bugs corrupt training | Med | High | Rule unit tests + invariant checks (cash conservation, ownership uniqueness) before any training |
| UI animation work overruns | Med | Med | Day-7 MVP cut line; static board first, animation second |
| Integration drift between engine/API/UI | Med | Med | Shared JSON schema (`TECH_SPEC.md` §6) frozen at end of Phase 1 |
| Unverified board prices questioned in viva | Low | Low | Documented decision D-007 + clear statement in report |
| IP concerns with the game look | Low | Med | Original name/art/cards (D-001) |
